# Requirements Document: Temporal v1.32.0 Compatibility

## Introduction

Tokeira claims behavioural compatibility with Temporal server `1.31.0` and vendors the
Temporal API protos at `v1.62.11` (`crates/tokeira-build-info/src/pinned.rs`). Temporal
released server `v1.32.0` on 2026-09-11. This spec is the **umbrella** for moving the
claim to `1.32.0`: it owns the campaign-level contracts that every slice shares — the
three pins, the vendored wire surface and its classified audit, the v1.32.0 configuration
denominator, the conformance fork branch and its baseline, the stock-posture decision,
and the final claim flip. It does **not** own any workflow behaviour. Every behavioural
delta between the two releases is owned by one of seven **delta specs** enumerated in
Requirement 9, each of which is authored, approved, and implemented on its own.

The compatibility authority for everything in this spec is Temporal server at tag
`v1.32.0` (commit `d94e34a1ebba5410a2e7d07119a76896909591aa`, `ServerVersion = "1.32.0"`
in `common/headers/version_checker.go:26 @ v1.32.0`) and the API version that release
pins, `go.temporal.io/api v1.63.5` (`go.mod @ v1.32.0`). Upstream `main` is already past
`v1.32.0` and is **not** an authority for this campaign.

This spec is foundational: it changes generated code across the workspace, adds a pin,
replaces the configuration denominator, and stands up a new conformance branch. Behaviour
work is deliberately sequenced after it so every checkpoint stays bisectable and green.

### Sibling work this spec depends on or defers to

- `.kiro/specs/proto-upstream-sync/` owns `tools/proto-sync`, `proto/UPSTREAM_VERSION`,
  and the checked-in generated bindings. Consumed unchanged.
- `.kiro/specs/temporal-api-v1.62-sync/` is the precedent for a proto bump; its Surface
  Audit vocabulary and structural properties are reused here.
- `.kiro/specs/temporal-compatibility/` governs the pins (Req 5.4–5.5 there: only
  conformance evidence moves the server claim; a proto bump alone never does).
- `.kiro/specs/release-process/` documents the server-compat bump protocol and the
  `Server-Compat-Bump:` trailer; its bump engine is unbuilt, so the flip is manual.
- `.kiro/specs/configuration-policy/` owns the extractor and the denominator format.
- `.kiro/specs/conformance-harness/`, `.kiro/specs/temporal-functional-conformance/`,
  and `.kiro/specs/conformance-config-override/` own the fork shim, the skip registry,
  and the override bridge.
- `.kiro/specs/activity-executions-first-class/` is absorbed by delta spec D1.

## Glossary

- **Target_Release**: Temporal server `v1.32.0`, tag `v1.32.0` in the Reference_Fork,
  commit `d94e34a1`. The behavioural authority for this campaign.
- **Target_API**: Temporal API `v1.63.5`, the `go.temporal.io/api` version pinned by
  Target_Release's `go.mod`. The wire authority for this campaign.
- **Claim**: the constant `TEMPORAL_SERVER_COMPAT` in `pinned.rs`. Currently `"1.31.0"`.
  Advertised as `GetSystemInfo.server_version`.
- **Proto_Pin**: the constant `TEMPORAL_PROTO_VERSION` in `pinned.rs`. Currently
  `"v1.62.11"`. Mirrors `proto/UPSTREAM_VERSION`.
- **Target_Pin**: a new constant `TEMPORAL_SERVER_TARGET` in `pinned.rs` naming the
  release under campaign (`"1.32.0"`) without asserting it. Equals the Claim when no
  campaign is running.
- **Upstream_Version_File**: `proto/UPSTREAM_VERSION`, a single line with no trailing
  newline, written by the Proto_Sync_Tool.
- **Upstream_Proto_Tree**: `proto/upstream/`, the vendored export of
  `buf.build/temporalio/api:<version>` plus Tokeira's hand-written
  `temporal/server/api/adminservice/v1/service.proto` and the OpenAPI copies.
- **Proto_Sync_Tool**: `tools/proto-sync`, invoked as `cargo run -p proto-sync -- <version>`
  (sync + generate), `-- generate`, or `-- check`.
- **Generated_Bindings**: `crates/tokeira-proto/src/generated/{upstream,tokeira}` and the
  service-proto copies under `crates/tokeira-compatibility/data/`, regenerated by the
  Proto_Sync_Tool and guarded by `tools/proto-sync/tests/reproducible.rs`.
- **Surface_Audit**: the table in this spec's `design.md` enumerating every proto-level
  delta between `v1.62.11` and `v1.63.5` with a classification and an owner.
- **Classification_Ignore / Classification_NoOp / Classification_Capability /
  Classification_WireThrough / Classification_Deferred**: the five audit buckets, with
  the meanings defined in `.kiro/specs/temporal-api-v1.62-sync/requirements.md`
  (Glossary) and restated in this spec's `design.md`.
- **Feature_Matrix**: `FEATURE_MATRIX` in `crates/tokeira-compatibility/src/matrix.rs`;
  the authoritative per-RPC ownership and state table. Its test
  `matrix_classifies_every_upstream_rpc` fails on any unowned RPC in the vendored protos.
- **Deferred_Stub**: a handler that returns gRPC `UNIMPLEMENTED` with a message naming the
  delta spec that owns the RPC, in the bracketed block style of
  `crates/tokeira-edge/src/grpc/workflow_service.rs`.
- **Stock_Rejection**: the exact status and message Target_Release returns for a feature
  that is gated off in its default dynamic configuration.
- **Reference_Fork**: the sibling checkout of `tokeira/temporal`, resolved per
  `AGENTS.md` §8, carrying the `v1.32.0` tag.
- **Conformance_Branch**: the fork branch `tokeira/conformance-v1.32.0`, rebased onto
  tag `v1.32.0`, carrying only the Harness_Shim and the skip registry.
- **Harness_Shim**: the Tokeira-owned files under `tests/testcore/` on the fork
  (`tokeira_conformance_cluster.go`, `tokeira_conformance_skip.go`,
  `tokeira_harness.go`, `tokeira_dynamic_config_bridge.go`,
  `tokeira_authorization_bridge.go`, `tokeira_metrics_bridge.go`, and their tests).
- **Pin_Gate**: `crates/tokeira-edge/src/conformance/pin.rs`, which refuses a
  conformance run unless the fork checkout is at the expected tag.
- **Denominator**: the pair `crates/tokeira-compatibility/data/temporal-<ver>-settings.json`
  (source facts extracted by `tools/temporal-config-audit`) and
  `temporal-<ver>-classification.json` (product decisions), verified by
  `crates/tokeira-compatibility/src/configuration.rs`.
- **Empty_Configuration**: an empty `tokeirad` TOML document; by the documented guarantee
  it selects the stock posture of the Claim's release
  (`docs/conformance/v1.31.0/README.md`).
- **Stock_Posture**: the behaviour Target_Release exhibits with its default dynamic
  configuration.
- **Delta_Spec**: one of the seven behaviour specs D1–D7 named in Requirement 9.
- **Ledger**: `docs/readiness/conformance.md`, the single measured-status surface.
- **Tier**: a row of `docs/readiness/functional-test-order.md`, one or more Go suites
  driven to green as a unit.
- **Baseline**: the recorded outcome of running the whole corpus on Conformance_Branch
  against an unchanged `tokeirad`, per suite: pass, fail, skip, unfinished.
- **Bump_Trailer**: the `Server-Compat-Bump: <reason>` commit trailer that
  `crates/tokeira-build/src/pipelines/ci.rs` requires on any commit changing the Claim.

## Target State

- The Upstream_Proto_Tree is the exact export of `buf.build/temporalio/api:v1.63.5`;
  the Proto_Pin is `"v1.63.5"`; a parity test ties Proto_Pin to Upstream_Version_File.
- Every one of the 123 `WorkflowService` and 12 `OperatorService` RPCs at Target_API is
  owned by exactly one Feature_Matrix entry. The six RPCs new in Target_API are served
  as Deferred_Stubs until their Delta_Spec lands the Target_Release behaviour.
- Every capability flag new in Target_API is advertised with an explicit value.
- The Target_Pin exists and equals `"1.32.0"`; the Claim stays `"1.31.0"` until
  Requirement 11 is satisfied; the Pin_Gate compares the fork tag against the
  Target_Pin.
- The Denominator is the verified `v1.32.0` set; the `v1.31.0` set is retired.
- Conformance_Branch exists at tag `v1.32.0` with a recorded Baseline, and every suite
  regression against the `1.31.0` Ledger is assigned to a Delta_Spec.
- Empty_Configuration selects the Stock_Posture of Target_Release (Requirement 12).
- After the seven Delta_Specs and the corpus drive-to-green, the Claim is `"1.32.0"`
  with the Bump_Trailer, the evidence table, and the `docs/conformance/v1.32.0/` folder.

Out of scope: any behaviour past tag `v1.32.0` (upstream `main`); implementing features
that Target_Release gates off by default (they are in-surface only as their
Stock_Rejection); reversing the deprecated Worker Versioning V1/V2 posture (unchanged in
`1.32.0`; removal is announced for `1.33.0`); the engine `0.4.0` release train (owned by
`.kiro/specs/release-engineering/`).

Sanctioned exceptions (Target_Release itself returns these, so Tokeira does too):

- Standalone-activity operator commands with an empty `workflow_id` return
  `UNIMPLEMENTED` `"Standalone activity operator commands are disabled"`
  (`chasm/lib/activity/frontend.go:43,457 @ v1.32.0`; gate
  `history.enableStandaloneActivityOperatorCommands` default `false`).
- Time skipping returns `UNIMPLEMENTED` `"The Time-Skipping feature is not enabled for namespace."`
  on `PollWorkflowExecutionTimeSkipping` and whenever a request carries a
  `time_skipping_config` (`service/frontend/errors.go:118`,
  `workflow_handler.go:713,7620 @ v1.32.0`; gate `frontend.WorkflowTimeSkippingEnabled`
  default `false`).
- Standalone Nexus operations return `UNIMPLEMENTED` `"Standalone Nexus operation is disabled"`
  (`chasm/lib/nexusoperation/frontend.go:34 @ v1.32.0`; gate
  `nexusoperation.enableStandalone` default `false`).

## Requirements

### Requirement 1: Proto resync to `v1.63.5`

**User Story:** As a Tokeira developer, I want the vendored Temporal API tree moved from
`v1.62.11` to `v1.63.5` in one atomic commit, so that the workspace builds against the
exact wire surface Target_Release ships.

#### Acceptance Criteria

1. WHEN the resync task runs, THE Proto_Sync_Tool SHALL be invoked as
   `cargo run -p proto-sync -- v1.63.5` from the workspace root and nothing else SHALL
   write to the Upstream_Proto_Tree.
2. WHEN the Proto_Sync_Tool completes, THE Upstream_Version_File SHALL contain exactly
   `v1.63.5`.
3. WHEN the Proto_Sync_Tool completes, THE Upstream_Proto_Tree SHALL contain
   `temporal/api/enums/v1/time_skipping.proto`, `temporal/api/sdk/v1/event_group_marker.proto`,
   `temporal/api/sdk/v1/external_storage.proto`, and `nexusannotations/v1/options.proto`.
4. WHEN the Proto_Sync_Tool completes, THE Generated_Bindings SHALL be regenerated and
   `cargo run -p proto-sync -- check` SHALL report no diff.
5. THE resync SHALL NOT modify `tools/proto-sync/`.
6. WHEN the resync commit is followed by the drift-fix commit, THE workspace SHALL pass
   `cargo check --workspace --locked`, `cargo lint --locked`, and
   `cargo nextest run --workspace --locked` with no behaviour change other than the
   registration of Deferred_Stubs (Requirement 3) and explicit capability values
   (Requirement 4).
7. WHEN the drift fix lands, THE Proto_Pin SHALL be `"v1.63.5"` and the tracked-ahead
   note in `pinned.rs` SHALL state that Target_Release ships `v1.63.5`, so the proto
   surface is no longer tracked ahead of the release it claims.
8. WHEN the drift fix lands, THE `crates/tokeira-proto/src/public.rs` OpenAPI document
   comments SHALL cite `v1.63.5`.
9. WHEN the drift fix lands, THE Claim SHALL still be `"1.31.0"`.

### Requirement 2: Surface Audit of `v1.62.11` → `v1.63.5`

**User Story:** As a reviewer, I want every proto-level delta enumerated, classified,
and owned, so that no new RPC, field, enum value, or message is absorbed silently.

#### Acceptance Criteria

1. THE Surface_Audit in `design.md` SHALL contain one row for every RPC, message, field,
   enum, and enum value added, removed, deprecated, or re-typed between `v1.62.11` and
   `v1.63.5`, derived from `diff -r` of the two vendored trees.
2. WHEN a row is Classification_Deferred, THE row SHALL name a target spec directory
   that exists under `.kiro/specs/` (a placeholder is acceptable).
3. WHEN a row is Classification_WireThrough, THE row SHALL have a matching row in the
   Implementation & Escalation Matrix with kernel impact `none`.
4. IF the resynced tree differs from the audit as drafted, THEN THE implementer SHALL
   amend the audit in the same commit as the fix, never leave the audit stale.
5. THE structural tests in `crates/tokeira-edge/tests/surface_audit_structure.rs` SHALL
   be extended to parse this spec's `design.md` with the same table grammar and SHALL
   enforce criteria 2 and 3.

### Requirement 3: Deferred stubs for the six new RPCs

**User Story:** As an SDK user, I want every `WorkflowService` method at Target_API to be
routable on `tokeirad`, so that a call to a not-yet-implemented RPC fails as
`UNIMPLEMENTED` with a message naming the owning spec rather than as a transport error.

#### Acceptance Criteria

1. WHEN the drift fix lands, THE `WorkflowService` implementation SHALL define handlers
   for `CountWorkers`, `PauseActivityExecution`, `UnpauseActivityExecution`,
   `ResetActivityExecution`, `UpdateActivityExecutionOptions`, and
   `PollWorkflowExecutionTimeSkipping`.
2. WHEN any of those handlers is called before its Delta_Spec lands, THE handler SHALL
   return gRPC `UNIMPLEMENTED` with a message naming the owning Delta_Spec from the
   Contract Policy table.
3. THE Feature_Matrix SHALL own each of the six RPCs in exactly one entry with state
   `Stubbed` and the owning Delta_Spec in its evidence, and
   `matrix_classifies_every_upstream_rpc` SHALL pass.
4. WHEN a Delta_Spec replaces a stub, THE replacement SHALL implement the Target_Release
   behaviour cited in the Contract Policy table, including the Stock_Rejection for the
   gated path.
5. THE OperatorService surface SHALL be unchanged (12 RPCs at both versions).

### Requirement 4: Explicit capability advertisement

**User Story:** As an SDK, I want every capability flag at Target_API to carry an explicit
server-chosen value, so that I take the code path the server actually supports.

#### Acceptance Criteria

1. WHEN `DescribeNamespace` or `GetSystemInfo` is served after the drift fix, THE
   response SHALL set every field in the "New capability fields" table to the value in
   its "Policy in this spec" column, written verbatim at the translator and never via
   `..Default::default()`.
2. THE test `capability_mappings_match_current_get_system_info_capabilities` in
   `matrix.rs` SHALL cover the new `GetSystemInfoResponse.Capabilities` field.
3. WHEN a Delta_Spec implements the feature behind a flag, THE Delta_Spec SHALL flip the
   flag and cite the Target_Release stock value it now matches.

### Requirement 5: Breaking-shape translation without behaviour change

**User Story:** As a Tokeira developer, I want the four re-typed or deprecated wire shapes
absorbed at the translation layer only, so that the resync changes no observable
behaviour before the owning Delta_Spec decides it.

#### Acceptance Criteria

1. WHEN the drift fix lands, THE edge SHALL compile against
   `temporal.api.common.v1.TimeSkippingConfig` on every message that carries it and SHALL
   continue to drop the field with the same disposition recorded in the v1.62 audit.
2. WHEN the drift fix lands, THE edge SHALL emit the same `BatchOperationType` values it
   emits today on `DescribeBatchOperation` and `ListBatchOperations`, and SHALL accept
   on `StartBatchOperation` whatever it accepts today; migration to the `*_WORKFLOW`
   values is owned by D2.
3. WHEN the drift fix lands, THE edge SHALL emit the protobuf default for
   `DescribeBatchOperationResponse.target_executions`, every `poller_groups_info`
   field, `TaskQueueStats.rate_limiting_active`, `StartWorkflowExecutionResponse.first_execution_run_id`,
   `QueryWorkflowResponse.link`, and `UpdateWorkflowExecutionResponse.link`.
4. WHEN the drift fix lands, THE `crates/tokeira-edge/UNSUPPORTED_FIELDS.md` file SHALL
   list every new request field the edge drops, each with its owning Delta_Spec.
5. WHEN the drift fix lands, THE binding inventory fixture
   `crates/tokeira-proto/tests/fixtures/binding-inventory.json` SHALL be regenerated
   from the `v1.63.5` bindings.

### Requirement 6: Configuration denominator at `v1.32.0`

**User Story:** As an operator reading the Feature Catalog, I want the complete, verified
set of Target_Release dynamic-config declarations and Tokeira's disposition for each, so
that every default flip between the releases is a recorded decision.

#### Acceptance Criteria

1. WHEN the denominator task runs, THE extractor SHALL be invoked as
   `tools/temporal-config-audit -repo <Reference_Fork> -tag v1.32.0` and its sorted output
   SHALL be committed as `crates/tokeira-compatibility/data/temporal-v1.32.0-settings.json`.
2. THE settings snapshot SHALL include declarations outside
   `common/dynamicconfig/constants.go`, including `activity.enableStandalone`,
   `activity.startDelayEnabled`, `history.enableStandaloneActivityOperatorCommands`,
   and `nexusoperation.enableStandalone`.
3. THE classification ledger `temporal-v1.32.0-classification.json` SHALL assign exactly
   one disposition, treatment, owner, conformance-override state, and evidence anchor to
   every key in the settings snapshot, and `configuration.rs` SHALL verify key-set
   equality against it.
4. WHEN a key was added, removed, or renamed between `v1.31.0` and `v1.32.0`, THE ledger
   entry SHALL record the change (including `matching.enableMigration` removed,

### Requirement 9: Seven delta specs own all behaviour

**User Story:** As the integration seat, I want every behavioural difference between the
releases owned by exactly one approval-gated spec, so that review happens once per
cluster and nothing lands as an unreviewed side effect of the campaign.

#### Acceptance Criteria

   house style (`requirements.md`, `design.md`, `tasks.md`) and ground-truthed to
   Target_Release:

     delay; `ACTIVITY_EXECUTION_STATUS_PAUSED`; the four `*ActivityExecution` operator
     RPCs; activity batch operations as Stock_Rejection; absorbs the open tasks of
     `activity-executions-first-class`.
   - `v132-batch-operations-and-workers` (D2) — `BatchOperationType` migration;
     `target_executions`; `ListWorkers` system-worker exclusion; `CountWorkers`;
     `PollerGroupsInfo`; `TaskQueueStats.rate_limiting_active`; `EnvironmentInfo`;
     poller auto-enroll capability.
   - `v132-visibility-query-converter` (D3) — unified query converter semantics.
   - `v132-worker-deployments` (D4) — one-time override; child versioning override;
     reactivation signals stock-on; demotion signal; dedup, delete-missing, trampolining
     fixes; error-text change; V1/V2 final-release posture verified unchanged.
   - `v132-nexus` (D5) — callback routing by URL scheme; `callback.allowedAddresses`;
     standalone Nexus operations as Stock_Rejection; SignalWithStart system endpoint;
     endpoint-not-found; metadata validation; `state_size_bytes`.

     stock-on; error-message truncation; `first_execution_run_id`; response `link`s;
     gated-off update callbacks, signal backlinks, SignalWithStart-from-workflow;
     schedule duration validation and scheduler-v2 fields.
   - `v132-gated-surfaces` (D7) — time skipping as Stock_Rejection plus
     `PollWorkflowExecutionTimeSkipping`; WFT completion pagination shapes; worker
     commands; external storage reference and event-group markers.
2. WHEN a Delta_Spec is drafted, THE spec SHALL be pushed as its own PR and SHALL NOT be
   implemented until the integration seat approves it.
3. WHEN a Delta_Spec is implemented, THE implementation SHALL replace the Deferred_Stubs
   it owns, flip the capability flags it owns, and tick its own `tasks.md`.
4. THE union of the seven Delta_Specs' scopes SHALL cover every regression and every new
   suite recorded in the Baseline; a finding that fits none SHALL be raised to the
